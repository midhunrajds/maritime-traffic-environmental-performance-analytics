### Storage types at a glance

- **AIS_POS:** `Date` is a nanosecond timestamp; `Mmsi` is unsigned 32-bit integer; `MessageType` is 32-bit integer; coordinates and several sensor/status fields are 64-bit floats; SOG/COG are 32-bit floats; position accuracy is Boolean; source/folder fields are strings; `id_chunk` is a list of strings.
- **AIS_SPEC:** `Date` timestamp; MMSI, IMO, dimensions, draught, and ETA components are unsigned 32-bit integers; message/type/position-fix codes are 32-bit integers; source, name, callsign, destination are strings.
- **AIS_ShipTypes:** code is numeric in the semicolon CSV; type labels and descriptions are text.
- **ERA5:** timestamp; lat/lon doubles; meteorological values are 32-bit floats; geometry is WKB binary.
- **CMEMS_PHY / CMEMS_WAV:** timestamp; depth/lat/lon and environmental variables are 32-bit floats; geometry is WKB binary.

The table above gives the full top-level field names; storage types are summarized here by field families. The canonical walkthrough is [`notebooks/01_data_audit_and_cleaning.ipynb`](../notebooks/01_data_audit_and_cleaning.ipynb); it prints the actual Parquet types, profiles missingness and keys for all datasets, and explains each cleaning decision before applying it.

Environmental Parquet files carry GeoParquet point geometry metadata with geographic CRS WGS 84 / EPSG:4326; `geometry` is WKB. AIS has numeric lat/lon in degrees but no CRS metadata. All six files store timezone-naive timestamps. We use their clock values as UTC without shifting them in the added `Date_utc`/`time_utc` fields: AIS report times are described as generated by the electronic positioning system and the AIS standard defines that timestamp in UTC seconds; ERA5 and CMEMS time axes are UTC. The local export schemas do not themselves retain timezone metadata, so this is an evidence-based project convention rather than a timezone encoded in each file.

## What each dataset contributes

- **AIS_POS is the movement/event table.** Each row is a vessel position report keyed by MMSI and report time, with navigation status, position, speed over ground, course over ground, heading, turn rate, and position-accuracy flag. It is the natural anchor for movement analysis. `SpeedOverGround` measures motion relative to Earth; it is not speed through water or fuel performance.
- **AIS_SPEC is a vessel-information message stream, not a clean vessel master.** Its records repeat per MMSI over time and contain type, dimensions, draught, name, callsign, destination, ETA, and position-fix type. Draught code 0 is unavailable; code 255 represents 25.5 m or greater and is upper-censored. Only codes 1–254 are converted to exact metres in the clean field ([IALA AIS guideline](https://www.iala.int/product/g1082/?download=true)). IMO number, name, draught, destination, and ETA are absent on about 68% of rows, so characteristics should be linked in time and their availability reported.
- **AIS_ShipTypes is the decoding lookup** for `AIS_SPEC.ShipType` codes. Its 256 unique codes map to a broad `Type` and `Additional` description; all type codes observed in AIS_SPEC are present in the lookup. Code 0 is labelled “Not available” and appears on 168,323 AIS_SPEC reports, so it should not be treated as an ordinary vessel category.
- **ERA5 supplies atmospheric context** on a coarser hourly grid: surface and mean-sea-level pressure (`sp`, `msl`), total cloud cover (`tcc`), 10 m east/west and north/south wind components (`u10`, `v10`), 2 m air temperature (`t2m`) and dewpoint (`d2m`). The field names follow ERA5 conventions. The MMDEC data paper specifies hPa, fraction 0–1, °C, and m/s. The local values match the stated pressure/temperature/wind units, but `tcc` is scaled 0–100 (max 100.00062), conflicting with the paper’s stated fraction. The clean output retains original `tcc` and adds `tcc_fraction_clean` divided by 100 with only the tiny float32 overshoot at 100% clipped. This is a documented source/export inconsistency; use the clean fraction in analysis. ECMWF native ERA5 units are Pa, fraction 0–1, K, and m/s, so pressure/temperature were transformed in the extraction.
- **CMEMS_PHY supplies near-surface ocean context** on an hourly grid. `so` is salinity, `thetao` potential temperature, `uo` eastward current, `vo` northward current, and `zos` sea-surface height. The local depth coordinate is only 0.494025 m. The values/ranges are consistent with salinity, °C, m/s, and m respectively, but units are not stored in the Parquet schema; the MMDEC data paper reports PSU, °C, m/s, and m respectively. [MMDEC data paper](https://tristanaverty.github.io/assets/pdf/averty2026mmdec.pdf) [Copernicus Marine global physics product manual](https://documentation.marine.copernicus.eu/PUM/CMEMS-GLO-PUM-001-024.pdf)
- **CMEMS_WAV supplies wave-state context** every three hours. `VHM0` is significant wave height; `_SW1`, `_SW2`, and `_WW` identify primary swell, secondary swell, and wind-wave partitions. `VMDR` and variants are mean directions; `VPED` is peak direction. `VCMX` is maximum crest-to-trough height; `VTPK` peak period; `VTM02`, `VTM10`, and `VTM01_*` are wave-period measures; `VSDX`/`VSDY` are Stokes-drift components. These variables conventionally use metres, seconds, degrees, and m/s as appropriate. The MMDEC data paper reports metres, seconds, degrees, and m/s for these fields. The clean output adds circular-normalized direction fields (`360° → 0°`) and `VMXL` is entirely null. [Copernicus Marine wave product manual](https://documentation.marine.copernicus.eu/PUM/CMEMS-GLO-PUM-001-027.pdf)

In short, **AIS_POS is the observation to explain**, AIS_SPEC and its lookup add vessel grouping, and the three environmental grids provide context at each position/time. The relation is not a direct key between AIS and the grid files: it requires a bounded time match plus nearest-cell or interpolation in space. Vessel reports should be attached using MMSI and an as-of time rule. Keep match distance, time offset, and missing exposure alongside the matched values.

The AIS position file contains 25,130 unique MMSIs; AIS_SPEC contains 23,958. All 23,958 AIS_SPEC MMSIs occur in AIS_POS. In AIS_SPEC the `ShipType` field has only 105 nulls, and the 256-row semicolon-delimited lookup is available to map numeric values. Join AIS_SPEC to positions using MMSI **and event time** (for example, a documented as-of rule); MMSI alone would replicate position rows across many AIS_SPEC reports and may leak later-reported characteristics backward in time. Type lookup is `AIS_SPEC.ShipType` → `AIS_ShipTypes.Code` after checking numeric/string normalization.

There are no direct identifiers connecting AIS to ERA5, CMEMS_PHY, or CMEMS_WAV. Integration requires a time and spatial operation (nearest grid point or interpolation with a stated maximum distance and time tolerance). A bbox-only scan finds 739,777 AIS rows outside ERA5's grid-coordinate bounds and 33,512 outside the CMEMS bounds; those points need an explicit edge/no-match policy. This is not the same as a final join-coverage estimate. The ERA5 file stops at Sep 30 00:00 while AIS continues to Sep 30 23:58; 200,179 AIS positions occur later than ERA5's final timestamp. CMEMS files include Oct 1 00:00, while AIS ends Sep 30.

All AIS MMSI, timestamp, latitude, and longitude values are non-null. AIS_POS scanned ranges have no out-of-range latitude/longitude and no negative SOG. Four rows are approximately 102.2 SOG; ITU AIS encoding reserves 102.2 knots or greater at its upper valid code, so these are upper-censored. A separate message-aware rule is also required: **22,106 raw Message Type 27 rows contain SOG value 63**, which the [US Coast Guard Message 27 specification](https://www.navcen.uscg.gov/sites/default/files/pdf/AIS/AIS_MSG27.pdf) identifies as unavailable. They are not treated as measured 63-knot reports in the cleaned field. After exact-event deduplication, 480,659 non-null COG values and 10,138,994 non-null heading values fall outside 0–359; these are excluded only from the added clean fields. ROT has 1,270,642 instances of -128, the “no turn information” default. We found **40,553 extra rows** sharing an `(Mmsi, Date)` key: 40,447 keys repeat, of which 106 occur three times. Across repeated-key records, every top-level field is identical, including provenance fields `chunk_folder` and `id_chunk`. The cleaner removes these confirmed duplicates only in the derived file and retains the raw source unchanged. AIS begins at 2023-06-30 23:58; 183 positions predate July 1. The project adds UTC-aware interpretation columns without shifting their timestamp values.

Local schemas do not declare environmental measurement units. The MMDEC data paper gives ERA5 units as hPa, 0–1 cloud fraction, m/s and °C; the local pressure, wind and temperature ranges match. Local cloud cover is stored as percent (0–100.0006), which conflicts with the paper. The cleaning output adds a fraction field by dividing local `tcc` by 100 and clips only the tiny float precision overshoot at 100%. CMEMS values are consistent with the source product's conventional units. Wave directions are circular; product documentation defines directions-from, and the clean copy maps 360° to 0° in added fields. AIS fields and environmental values must not be physically interpreted solely from abbreviated column names.

AIS_SPEC has 10,636 extra rows on repeated `(Mmsi, Date, MessageType)` keys (10,633 repeated keys; three keys appear three times). Of the extras, 10,601 repeat the full row exactly; 35 have differing fields, most commonly source. Clean copy removes the exact repeats only. The data paper documents the `ImoNumber` 10,000,000–1,073,741,823 codes as official flag-state numbers, so those large values are valid AIS field semantics rather than corrupt IMO numbers. Do not deduplicate this dataset using the three-field key alone. The lookup CSV has 256 unique, fully populated codes and no duplicate codes; every one of the 95 distinct ship-type codes observed in AIS_SPEC maps successfully. The mapping resolves code 0 to “Not available.”

AIS_POS field missingness varies sharply by `MessageType`: types 18 and 19 have no `NavigationStatus` or `RateOfTurn`, and type 27 has no `TrueHeading` or `RateOfTurn`; these fields are populated in position messages 1/2/3. Therefore, a global null percentage overstates missingness for fields not carried by each message type. Among unique `(Mmsi, Date)` events, median observations per vessel are 242.5; 756 of 25,130 MMSIs have only one timestamp. The 5.5-hour p99 gap and sparse coverage caution against assuming continuous trajectories or deriving maneuver dynamics without gap filters.

## Linkage and analytical feasibility

- **AIS_POS ↔ AIS_SPEC:** MMSI overlap is complete for AIS_SPEC in these files. AIS_SPEC has 13.56 million records over 23,958 vessels and substantial repeated messages; use a temporal join and preserve the message time/source/type for auditability. MMSI alone is not a unique row key.
- **AIS_SPEC ↔ AIS_ShipTypes:** join by normalized code. The lookup has unique codes 0–255 and covers every observed AIS_SPEC code; 161 codes are not observed locally. Exclude or label code 0 as “not available,” not as a normal vessel group.
- **AIS ↔ environmental grids:** both have latitude/longitude and temporal coverage for most of the quarter, but no row-level foreign key. Match by space and time, preserve match distance/time offset, test edge coverage, and quantify null environmental exposure before analysis. Avoid an unconstrained many-to-many join.
- **Original question feasibility:** speed-versus-weather/ocean *association* is feasible as an exploratory question after documented spatiotemporal matching and vessel/route/traffic controls. The data have no observed fuel consumption or engine performance, AIS_SPEC vessel characteristics are sparse for several fields. Environmental variable definitions were compared with the MMDEC data paper; the local cloud-cover scale discrepancy is documented. These files alone cannot establish environmental causation, fuel efficiency, or vessel technical performance. AIS traffic density and vessel-type/corridor differences are defensible baseline analyses.

## Operational question and completed analysis

The intended user is a fleet operations or voyage performance analyst. The study asks whether wind, current, and wave conditions improve estimates of observed vessel speed over ground beyond a baseline that accounts for vessel category, route/location, time, and local AIS traffic. A useful output would be a context-aware reference for reviewing recurring slow-speed areas or individual segments after a voyage. It is a screening aid for human review, not an automatic operational recommendation.

The joined sample was checked over 10–30 km candidate distance limits. At 20 km, 89.0% of the 50,000 positions had all three environmental matches, with 18,241 moving reports available for pooled correlation. Spearman correlations of speed with wind speed, current speed, and significant wave height were 0.134, 0.124, and 0.187. These weak relationships are descriptive and do not account for vessel, route, or traffic context.

The model comparison is complete. A local AIS traffic measure was built from distinct vessels per 0.1-degree cell-hour. A context-only Ridge regression was compared with one adding wind, current, and wave inputs using five 80/20 splits grouped by MMSI. In the primary sample of 18,110 reports from 8,621 vessels, mean MAE was 2.603 kn for context only and 2.588 kn with environment (0.59% reduction); mean R² was 0.386 and 0.391. This is a small improvement in the tested quarter, grid matching, and model family. It supports using the result as retrospective context for analyst review, not as a speed recommendation. The evaluation does not yet test a later time period or another sea area. Findings are predictive/descriptive, not causal.

This use case does not measure fuel consumption, emissions, engine load, safe speed, or operational efficiency. Those claims need additional vessel-specific and voyage data. The GitHub-facing purpose and limitations are summarized in [`README.md`](../README.md).

## Reproducibility notes and limits of this inventory

Parquet row counts and schemas came from file metadata; missingness came from Parquet row-group statistics and location-level checks; MMSI/type linkage, timestamp/grid coverage, coordinate ranges, AIS value flags, duplicate keys, per-vessel interval summaries, and environmental grid-key uniqueness were calculated using column-projected scans. AIS code interpretation uses the [ITU-R M.1371 AIS technical recommendation](https://www.itu.int/epublications/en/publication/itu-r-m-1371-6-02-2026-technical-characteristics-for-vhf-automatic-identification-system-using-time-division-multiple-access-in-the-maritime-mobile-service). The ship-type CSV uses `;`, not comma. Raw files were not changed. Track-jump review and unit/time convention review are documented in `docs/cleaning_log.md`; spatial-temporal matching, association checks, and model comparison are in [`notebooks/04_relationships_and_match_coverage.ipynb`](../notebooks/04_relationships_and_match_coverage.ipynb). The project now includes a README overview; the required packages and versions are listed in [`environment.yml`](../environment.yml).
